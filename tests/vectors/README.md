# Conformance vectors

Cross-implementation test vectors for the crypto suite and current wire formats,
including the v2 ballot signature that covers the eligibility credential. These are this project's **own** canonical vectors; any conformant
implementation (this Python crypto layer, the TS frontend SDK, a future port)
must pass the vectors for the conformance level it claims. Passing them is the protocol conformance gate.

**Schema:** JSON with hex-encoded points and byte blobs. Integer representations
vary by fixture: numbers, decimal strings and `0x`-hex strings are all used.
Most verification fixtures have `{name, description, version, inputs, expected}`;
pinned build fixtures also use `outputs`, the election fixture has top-level
`config`/`ballots`/`aggregate`/`shares`/`result`, and scaling fixtures use `cases`.
Read the category's test loader for the exact schema.

## Categories

Adopted from the reference SDK's cross-language suite (verified by the Python implementation
in `tests/test_conformance_vectors.py`):

- `encrypt/` — ElGamal ciphertext byte-parity under pinned randomness
- `dleq/` — Chaum-Pedersen DLEQ verify
- `or/` — (B+1)-branch OR proof verify
- `budget/` — exact + atMost budget proof verify
- `schnorr/` — Schnorr signature verify
- `decrypt-share/` — decryption-share DLEQ verify
- `ballot/` — full ballot validity-proof + signature (variant A / exact = level 1;
  current signatures include the attestation; `ballot_swapped_credential` must fail).
  The loader skips unsupported Variant B / atMost full ballots as level 2.
- `tally/` — Lagrange combine + BSGS recovery

Repository-specific attestation, ballot and election fixtures can be generated by
`scripts/gen_vectors.py`:

- `attestation/`: weighted `ATTESTATION_V1`, with positive **and** negative cases
  (tampered weight, tampered nonce, wrong-election binding), plus a large weight
  (50) that must verify. `weight + q` and `nonce + q` must **fail**: a verifier must
  reject values at or above the curve order instead of reducing them. `weight` and
  `nonce` are decimal strings so readers that round JSON numbers above 2^53, such as
  JavaScript, get the exact value; parse them with `BigInt(...)` or `int(...)`.
- `flow/` — a complete variant-A/exact/weighted election (config, 5 ballots incl.
  one invalid + one duplicate, aggregate with exclusions, a `t`-share quorum, result),
  replayable to reproduce the admitted set, aggregate, and tally

The separate scaling fixture is maintained alongside these:

- `scale/` — integer half-up rounding, including boundary cases; checked by
  `test_scaled_weight_vector`

Build-style fixtures (`*_known.json`) pin all randomness and are checked for
exact byte reproduction by `tests/test_parity_vectors.py`.

## Running the gate

```sh
pytest tests/test_conformance_vectors.py tests/test_parity_vectors.py
```

These commands run the Python side of the compatibility checks. The frontend
uses the external `@shutter-network/urban-verified-crypto` SDK (currently 0.3.0).
Its separate TypeScript parity harness must consume the same fixtures to check
both implementations; `npm --prefix frontend test` does not run that harness.

`python scripts/gen_vectors.py` regenerates the attestation, ballot and election
fixtures. It does not regenerate every category or the pinned `*_known.json`
fixtures. Some generated fixtures use fresh randomness, so regeneration can
change bytes; it is not a read-only verification command.
